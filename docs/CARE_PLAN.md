# План спостереження

Розділ «План» перетворює наявні клінічні уточнення на перегляд рішень: які дані потрібні, коли повернутися до оцінки, які перевірки пов’язані та як можливий результат вплине на висновок.

## Поточна версія

- 17 пунктів відповідають 17 незміненим крокам `Candidate.workup`.
- 8 зв’язків показують клінічний контекст між перевірками. Вони не є доказами причинності або забороною виконувати інший крок.
- Фільтр за клінічним питанням, повний план, пошук і переходи між пов’язаними кроками.
- Результати в блоці сценаріїв є можливими: вибір показує інтерпретацію та не записує результат обстеження.
- Джерельні дані й положення настанов відкриваються з відповідного рішення.
- Виконання відображається тільки за `workflow_records`. Для цього знімка таких записів немає.

Строки, відповідальний і прийняття лікарем залишаються неузгодженими. Нового поточного стану пацієнтки, призначень або результатів система не створює. Це представлення вже виконаного синтезу з проєктом організації наступного перегляду. Нового клінічного синтезу, автоматичного моніторингу стану чи сповіщень у цій версії немає.

## Контракт даних

Опційне `presentation.complications.care_plan` має схему `hematoboard.care-plan-projection/0.1`. Воно зв’язане з точними `candidate_sha256` і `graph_state_sha256`.

Кожен пункт містить `workup_id`, хеш повного незміненого кроку, коротку мету рішення, потрібну інформацію та клінічний момент перегляду. `owner`, `due_date` і `clinician_decision` у цій версії мають бути `null`. Вони не заповнюються датою побудови сайту чи модельною здогадкою.

Залежність посилається на два кроки й зберігає точне `rationale` як підставу. Контекстні зв’язки не спрямовуються на невідкладний крок: планове уточнення не повинно затримувати невідкладну оцінку.

`validateCarePlanBindings` відхиляє іншу ревізію, втрату чи дублювання кроку, зміну його клінічної підстави та ненульові `owner`, `due_date` або `clinician_decision`. Валідація виконується в браузері та через `npm run verify`. Вона перевіряє структуру й хеші; клінічну коректність тексту представлення має оцінити лікар.

## Інтеграція з HematoBoard

`CarePlanView` отримує `Bundle`, обране клінічне питання й чинний `ComplicationsHost`. Відсутність нового поля повертає попередній `ClearPlan`; інші кейси не потребують міграції.

`onOpenSource` відкриває точні джерела. Опційний `onRequestWorkupUpdate` може передати кейс, хеш Candidate та ID кроку обробнику застосунку-хоста. Сам виклик не зберігає запис виконання; відповідний робочий процес має реалізувати хост. У публічному сайті цього обробника немає: браузер не зберігає медичні записи й не імітує лікарське прийняття.

Подальша робоча інтеграція потребує актуалізованих даних, документованого рішення лікаря й записів виконання в клінічному ядрі. Новий факт надходить через чинний Source Reading → Patient Graph маршрут; зміна причинного висновку — через клінічну ревізію. Майбутня дата контролю є елементом прийнятого плану, а фактичний результат — окремим спостереженням.

## Дизайн

Збережені Material-компоненти, наявні кольори, шрифт, навігація та джерельна панель. Стилі розділу в `src/safety/care-plan.css` використовують наявні змінні та селектори всередині `.hb-complications`. Фіолетові зони позначають структуру й вибір, теплий акцент — пріоритет перевірки, червоний — умовний невідкладний маршрут. Колір не встановлює тяжкість або причинність.

На широкому екрані перелік рішень і вибране рішення розташовані поруч. На вузькому перелік замінює підписаний селектор. Пріоритет, умови інтерпретації та стан виконання зберігаються в обох представленнях.

## Оновлення й перевірка

Після перевіреного редагування тільки представлення:

```sh
node --experimental-strip-types scripts/refresh-presentation-release.mjs
npm run verify
npm test
npm run build
```

Скрипт оновлює хеш представлення й журнал його ревізій. Він підготовлений для цієї зміни від 10.11.2026; для наступної ревізії потрібно оновити в ньому дату й підставу запису. Він відмовляється працювати, якщо змінився клінічний пакет або граф. Зміни цих артефактів потребують їхнього власного маршруту публікації.

Регресійні перевірки покривають незмінність клінічної підстави, повноту плану, чужу ревізію, вигадані дати й виконавців, залежності та сумісність попередніх проєкцій. Перед публікацією також перевіряються браузерні переходи, сценарії, джерела, пошук і адаптивність.
